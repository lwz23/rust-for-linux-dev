``nlmon -> rnull`` 后的 Rust 化流程修订记录
==========================================

摘要
----

本文档记录 ``nlmon`` 首轮流程在 ``rnull@v6.10`` 盲写实验后暴露出的缺口，以及因此新增的
硬规则。它的用途不是替代完整手册，而是明确回答：

- 原来的 ``nlmon`` 流程哪些部分仍然成立
- 哪些地方必须升级，才能更接近官方初始 upstream 的工程标准

哪些规则保持不变
----------------

下面这些主干顺序仍然成立，并且已经被 ``nlmon`` 与 ``rnull`` 两轮实验共同验证：

1. 先接通 Kbuild/Kconfig。
2. 先扩主 bindgen，再做缺口审计。
3. 只有主 bindings 无法覆盖的 inline/宏盲区，才补最小 helper。
4. 所有 ``unsafe`` 必须下沉到 ``rust/kernel/*`` 与极小 helper。
5. 驱动层保持零 ``unsafe``。
6. 保留原始 C 实现作为功能金标准。
7. 用脚本化构建、QEMU 与差分测试做闭环验证。

这说明 ``nlmon`` 流程并没有走偏；它的问题不是主干顺序错误，而是**收敛标准还不够硬**。

新增的硬规则
------------

1. blind-first 只算 ``prototype-grade``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``nlmon`` 流程此前更强调“先做出一个零 ``unsafe`` 的可运行版本”。``rnull`` 证明这一步是有
价值的，但只能得到 ``prototype-grade`` 结果，还不能直接宣称接近主线工程质量。

新规则：

- 任何新模块 Rust 化都必须先明确：

  - ``blind-first bootstrap``
  - ``upstream alignment & abstraction hardening``

- 第一阶段通过，只能说明“这条路走得通”。
- 只有第二阶段完成，才允许写“工程验收”或“接近主线级”结论。

2. 官方初始 upstream 对比变成强制阶段
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

此前 ``nlmon`` 手册把官方实现对比更多看作经验性参考。``rnull`` 证明这不够。

新规则：

- 如果目标模块已经有官方初始 upstream Rust 实现，那么：

  - 对齐它的对象模型和 API 形态是强制阶段
  - 不能只对齐功能而忽略抽象边界

- 对比基线优先级固定为：

  1. 原始 C 实现
  2. 官方初始 upstream Rust 实现
  3. 之后才视需要看最新主线成熟版

3. intrusive / registered / callback-owned 对象默认优先主线式建模
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``rnull`` 最重要的教训是：某些对象如果不在一开始就按主线常用模式建模，blind-first 非常容易
产出“能跑，但不够健全”的 safe API。

新规则：

- 对 intrusive / registered 对象默认优先 ``Pin + Opaque``。
- 对 request、buffer、callback-owned 对象默认优先显式状态机。
- 对参数受限对象默认优先 builder 前置校验。
- 如果想偏离这些默认模式，必须写出结构性理由，而不是因为“当前最省事”。

4. ``unsafe`` 审计必须覆盖后置条件
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

此前流程虽然已经强调前置条件，但 ``rnull`` 证明仅检查“调用时合法”还不够。

新规则：

- 所有 ``unsafe`` 审计都必须同时覆盖：

  - 前置条件
  - 后置条件
  - 所有权转移
  - 生命周期边界
  - 析构配对
  - safe API 调用者为什么无法破坏这些条件

5. ``unsafe impl Send/Sync`` 默认禁止
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``rnull`` blind-first 阶段曾暴露出过宽 ``Send/Sync`` 断言的问题。

新规则：

- ``unsafe impl Send/Sync`` 默认禁止自动生成。
- 若确实需要，必须在审计文档里写明结构性证明。
- “当前测试没出问题”不是可接受理由。

6. helper 既要做引入审计，也要做退役审计
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``nlmon`` 阶段主要强调“不先写 helper 再补 bindings”；这仍然正确，但还不够。

新规则：

- helper 只能在主 bindings 缺口已经审计确认后生成。
- 进入官方初始 upstream 对齐阶段后，必须再检查：

  - helper 现在是否仍然必要
  - 是否已经有更主线化的绑定/抽象路径

- 若 helper 已不再必要，必须删除或至少显式标记为过渡遗留。

7. 原型聚合对象不能直接进入最终抽象
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``rnull`` blind-first 阶段出现过 ``Registration<T>`` 这类“把多个生命周期揉在一起”的原型
聚合对象。

新规则：

- ``blind-first`` 阶段允许为跑通路径引入临时聚合器。
- 但在 hardening 阶段，必须把它们拆回更细粒度、生命周期更清楚的对象流。

对手册的直接影响
----------------

基于以上修订，后续手册和开发说明必须统一采用下面口径：

- ``blind-first`` 只算原型，不算主线级。
- 官方初始 upstream 对比是强制阶段，不再是“可选参考”。
- 对象模型不仅要看功能，还要看：

  - ``Pin``
  - 状态机
  - builder 校验
  - ``Send/Sync`` 断言
  - helper 是否仍必要

- 工程验收结论必须建立在 hardening 之后，而不是建立在第一次跑通之后。

当前结论
--------

``nlmon`` 流程的主干顺序已经被证明有效；``rnull`` 让我们确认了还需要再补上一层更严格的
收敛标准。

因此，后续更合适的流程标准应当是：

- **先用 ``blind-first`` 证明旧树上能独立跑通**
- **再用官方初始 upstream 对齐与抽象 hardening 把原型收缩成更主线化的实现**
